# ADR 0040 · Snapshot-bound acceptance matrix

Date: 2026-09-24<br>
Status: Accepted for P3-05 on the Python Core path

## Decision

Python Host projects every criterion from the approved current Task Contract into a distinct acceptance state. The matrix is bound to that Contract revision and the latest immutable CodeSnapshot of the Task. A later Contract revision or development snapshot invalidates earlier criterion decisions for the current matrix without deleting history. Renderer receives a fixed `run.acceptanceMatrix` read command and can submit only `run.acceptanceDecide` with Project/Task/snapshot/revision/criterion, an explicit decision status, optional opaque Verify report ID, a reason and an idempotency key. Electron Main only validates/forwards the fixed command over versioned JSON-RPC stdio. It cannot access SQLite, run SQL or execute a check.

A Verify report proves a named command ran on a fixed snapshot; it does not prove an arbitrary acceptance criterion. The matrix therefore starts automated criteria as `unverified` and manual/inspection criteria as `manual`. An explicit local-user mapping can mark an automated criterion `verified` only with a current-snapshot `passed` report whose exit code is zero. A failed check cannot be marked verified. Human decisions can record `failed`, `risk_accepted` or reasoned `not_applicable`; manual/inspection `verified` requires a written basis. Decisions are append-only, project-scoped, idempotent and rejected for stale snapshot/Contract, untrusted or inactive Project, foreign report, unknown criterion, invalid payload or detected sensitive text. The UI displays the report, criterion state and reason together. It does not infer a pass from stdout, a Review `approved`, or a Development Run `succeeded`.

`evaluation` is `inconclusive` when a required criterion lacks a current decision, `failed` when a required criterion is explicitly failed, and `covered` when every required criterion has a current `verified`, `risk_accepted` or `not_applicable` decision. `covered` means the checklist has explicit coverage; it is **not** a Task pass or final approval. `finalAcceptanceRequired=true` remains true in every response. The current single-user Desktop bridge supplies the local-user context but v19 does not store a principal/versioned Owner acceptance record; P3-07 owns that fresh decision, Task→Done transition, review/check freshness and safety gates. P3-06 owns bounded rework. P3-08 owns merge. No decision here triggers any of those transitions.

Additive SQLite migration v19 creates only immutable `acceptance_decisions` linked to existing Project, Task, CodeSnapshot and optional Verify report. It preserves v1–18 and does not reset user data. This narrow production table is the P3-05 implementation of the reference `verification_results` intent, without copying the full future Artifact/Workflow schema. The reference `step-result.schema.json` allows `pass/fail/unverified/not_applicable`, while reference SQL also lists `waived`; the matrix keeps `risk_accepted` distinct from `verified` rather than silently extending immutable StepResult enum. P3-07 will map a final human risk decision to a formal waived outcome if that acceptance contract requires it. The reference files remain read-only.

## Evidence and limits

Real macOS arm64 Git/SQLite/subprocess tests confirm a completed Development Handoff with unverified AC does not become Done, a passed command still leaves the criterion inconclusive until explicitly linked, a failing command cannot be linked as verified, an explicit risk decision keeps its reason, idempotent replay and restart retain the decision, stale/foreign evidence is rejected, and source Git stays clean. Independent Python Host stdio tests exercise the fixed commands. Real Electron Renderer→Main→Python Host→Codex on a disposable Git fixture presents the matrix UI and records an explicit report/criterion link; the screenshot and IDs are in implementation status. The Task remains without final human acceptance.

This does not parse test-framework case counts or semantic assertion coverage. Human mapping must explain how the check relates to the criterion. It is not an OS sandbox for project scripts. Existing user DB v18→19 migration, Windows x64, macOS Intel, installer packaging, Host hard-crash recovery and future generalized artifact imports are unverified. No new direct dependency, credential, local TCP server or global tool was introduced.
