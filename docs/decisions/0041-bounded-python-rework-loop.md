# ADR 0041 · Bounded Python Review and Verify rework

Date: 2026-09-24<br>
Status: Accepted for P3-06 on the Python Core path

## Decision

The Python Host alone owns rework. A persisted `changes_requested` Review report with a `ReworkHandoff`, or a persisted nonzero-exit `failed` Verify report, may reserve one rework cycle for its **current** CodeSnapshot. The source Development Run must have succeeded with an immutable Handoff and frozen RunConfig. The Project must remain active and trusted. A unique source-snapshot constraint and durable next Run ID make duplicate report delivery idempotent; a competing Review and Verify failure for one snapshot cannot launch two writers.

One rework cycle creates a **new Run containing the next numbered Developer Attempt** for the same approved Task. Its configuration copies the source workflow/profile/plugin/model/budget and requires the same Task and Environment revisions. The new owned Git worktree starts at the failed snapshot's pinned commit, whose Forge ref and tree are checked. This preserves prior changes without writing to the user's source worktree or repurposing the old Attempt's epoch. Review or Verify feedback is taken from immutable Host reports, clipped and provenance tagged, with failure kind/exit, bounded redacted output or blocking issue, current diff when available, and cycle/total-attempt counts. The original approved Task AC and scope remain present in the bounded ContextBundle. No raw provider event or unbounded log is promoted to Core authority.

The two rework routes share one Task-level cycle count. The current standard preset permits at most three cycles and twenty total Development/Review/Verify attempts. Every Developer Run also retains its frozen finite duration/tool/token budget. After the new snapshot is frozen, Host restarts only the **same gate** that failed: the original read-only Reviewer model or the original approved Verify CommandPreset and kind, using a deterministic idempotency key. A gate that cannot be started fails closed to `blocked`; it never invents a report. Repeated failure at the cycle or total-attempt ceiling records `REWORK_LIMIT_REACHED`, creates no new Run, and projects the Task as blocked in the Development column. A cancelled rework Run remains cancelled, and no gate starts after it. Human acceptance and Task Done are still separate P3-07 decisions.

SQLite migration v20 appends `rework_cycles` without altering v1–19 or deleting user Project/Task/Run data. Only Python Host reads or writes this table. Renderer receives a fixed, project-scoped `run.reworkCycles` read command and a typed diagnostic list; it cannot choose a command, count, executable, worktree path, model or payload for automatic rework. Electron Main only validates and forwards the fixed protocol. The historical Node Host rejects the new command as unknown and is not a fallback.

## Evidence and limits

On macOS arm64, disposable real Git repositories, SQLite, Host services, approved check subprocesses and owned Developer subprocesses exercised Verify fail→new snapshot→automatic Verify pass, Review blocker→new Developer Attempt with provenance-tagged handoff, mixed route reservation, repeated Verify failure→fourth trigger blocked, twenty-total-attempt ceiling, and cancellation during a live rework process. Replayed failure returns the same cycle. New snapshot acceptance remains unverified until a separate explicit decision. Source Git remains clean. Full quality chain, real Electron smoke/schema 20 and authenticated Electron→Python Host→Codex development/Verify regression are recorded in implementation status.

The Review test uses a persisted structured fixture result and no fake read-only capability; its follow-up Reviewer is deliberately blocked because that unit fixture has no persisted ReviewJob. The production path uses the real read-only Reviewer job/model. A live Codex `changes_requested`→automatic re-review loop has not been forced and remains a separate provider regression. Host hard-crash side-effect reconciliation is T034/P3-09; pending or launching cycles become interrupted on restart and never silently replay. The current user database upgrade, Windows x64, macOS Intel, installer, cost values unavailable from a provider, and long-running cross-version migration are unverified. No new dependency, credential, local server or global tool was introduced.

## Desktop gate recovery addendum · 2026-09-26

An automatic follow-up Review/Verify launch can fail after the new Developer snapshot already exists. Keep the persisted `blocked` cycle and its reason for diagnostics. A user may start the **same** gate through the existing Desktop control after fixing the missing capability or environment. The read projection clears `REWORK_UNRESOLVED` only when a completed Host-owned job on that exact next Run and snapshot has a latest successful report (`approved` Review with the original model and exact Reviewer Profile ID/revision/hash, or `passed` Verify with the original kind and frozen preset). No report for a different Run, snapshot or gate can recover it. `REWORK_LIMIT_REACHED`, interrupted cycles, failed reports and missing jobs remain blocked. The latest Review/Verify evidence still participates in the normal Owner acceptance basis hash and all other acceptance gates; recovery itself never marks a Task Done. This is a read-side reconciliation of immutable reports, without a migration or a new Renderer command. A real Git/SQLite/process fixture covers failed automatic Verify start followed by a real manual Verify report, and a Review failure fixture confirms the wrong gate cannot recover it. The Codex online Review blocker route remains separately unverified.

The automatic Review launch now carries the source Host ReviewJob's locked Reviewer Profile ID and revision as well as model. A follow-up may not silently fall back to the built-in Reviewer when the original profile is unavailable. A selected Developer Profile's `maxSeconds` is copied into each new Run's frozen duration budget, bounded by an admitted published workflow's Develop-node timeout. A rework Run keeps the source Run's frozen budget even if the Profile changes later. The existing `maxTurns`, `maxTokens`, and `maxToolCalls` RunConfig fields were not claimed to be fully enforced provider limits at this checkpoint; the scheduler only used `maxTurns` for bounded no-side-effect launch retries. No duration change is retroactively applied to a running Run.

## Observed Run budget stop addendum · 2026-09-26

The Python Host now compares each validated `usage.updated` event against the immutable RunConfig `maxTokens`, and each started command/tool against `maxToolCalls`. For a locked Developer Profile, it also compares provider-reported output tokens with that exact Profile version's `maxOutputTokens`. The Desktop may edit the latter for the next Profile revision. On first observed overrun the scheduler requests the owned Executor to stop, confirms the owned process tree has exited, then records a **failed** Run with a closed `RUN_*_BUDGET_EXCEEDED` reason. If exit cannot be confirmed, existing quarantine/interrupted handling remains in force. An explicit user cancel still records cancellation separately. The existing `run.failed` audit event carries the reason because historical SQLite `run_events` has a closed event-type constraint; no table rebuild or user data migration was performed. Run inspection and the normal Desktop detail view show the actual reason and frozen limits.

The installed Desktop QA build `desktop-data-switch-final-20260926` exposed that the original 50,000 total observed-token default can stop even a small real Codex coding fixture before a file change: one Run failed at 64,318 input / 379 output tokens with `RUN_TOKEN_BUDGET_EXCEEDED`. This was a correct fail-closed result, not a delivered task. To let the user deliberately allocate more of the existing authorized Codex quota to a particular run, the Desktop start form now offers exactly 50,000 (unchanged default), 100,000, or 200,000 observed tokens. The optional choice is validated by both public command schema and Python Host, then frozen into that RunConfig; rework continues to reuse the source budget. It does not change an old Run, add a credential, automatically restart a failed Run or claim a precise monetary cap. A higher choice requires an explicit user selection before Start, and provider usage events can still arrive after the threshold.

These are observation-driven stops, not provider-side exact caps: upstream usage can arrive late, so tokens or tool calls may exceed the configured number before Forge can interrupt. A Development Run starts one app-server turn, while Codex may make multiple internal model/tool steps within that turn; Profile `maxTurns` is still **not** a verified bound on those internal steps. Cost can remain unavailable. T119 remains deferred until a real provider loop, time/token/turn budgets, full consumption accounting and human escalation are tested together. The no-fee Python fixture test uses a real owned child process, validated usage/tool events, verified stop, released workspace lease and clean source Git; it does not claim an online Codex budget run or a hard provider limit. No new dependency, protocol version, credential path, network listener or permission was added.

Codex `thread/tokenUsage/updated` reports `total` for the lifetime of its thread, while `last` reports the most recent response. A rework Run can resume that thread; counting its lifetime `total` against the new Run's frozen budget would charge earlier work again. On the first usage event for the current turn, the adapter subtracts `last` from `total` to establish the earlier-thread baseline. Every later event reports `total - baseline` as this Run's cumulative input/output/cache usage. Duplicate total events do not double count. A missing or decreasing counter fails the Run as a protocol error rather than producing an unreliable budget result. This is a wire-normalization change under the existing Executor Event contract. The pinned Codex CLI's generated protocol schema requires both `total` and `last`; the offline resumed-thread fixture covers large prior usage, two new responses, duplicate notification and counter reset. An online resumed Run with a deliberately tripped budget remains unverified.

## Reviewer result version binding · 2026-09-26

An installed-app Reviewer returned a valid snapshot/task/contract identity but guessed `profileRevision=2` from contract revision 2; the built-in Reviewer was frozen at profile revision 1. Forge correctly rejected this as `REVIEW_RESULT_STALE`, retained the failed ReviewJob and produced no report. The request had included `ReviewContext` but had not explicitly supplied the separate Reviewer revision. The Host now supplies all four exact result bindings in the read-only Reviewer request. Result evaluation still rejects any mismatched value. The Host passes the frozen Attempt's Reviewer revision into report validation and storage, so a published custom Reviewer revision is checked against its own lock rather than against the built-in preset. No Renderer command, schema migration, privilege, approval rule or automatic retry was added. A new installed-app Reviewer approved the same retained snapshot; the approved Verify command, per-criterion decision and Owner acceptance then produced a durable delivery. The earlier failed ReviewJob remains failed history, and the original source Git repository remained clean.
