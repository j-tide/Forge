# ADR 0042 · Snapshot-bound final human acceptance

Date: 2026-09-24<br>
Status: Accepted for P3-07 on the Python Core path

## Decision

The Python Host alone owns final human acceptance. Its read model identifies the approved Task Contract revision, latest immutable CodeSnapshot, current Development Run, Review report, Verify reports and per-criterion AcceptanceDecisions. A canonical SHA-256 basis includes the content hashes and stable IDs of these sources. The Renderer must first read this basis, display the current evidence, and submit its expected snapshot, Contract revision and basis hash with an explicit decision and reason. The Host recomputes them inside an SQLite write transaction. An old snapshot, changed report, changed AC decision or new Run is rejected as stale. The fixed local stdio bridge rejects unknown fields and does not accept an actor, SQL, file path, shell command, merge or deployment instruction.

Acceptance is allowed only for the current succeeded Development Run, an approved Review, a covered required-AC matrix, no failed current Verify report, no open current Review advisory and no active Review/Verify/Run or unresolved rework. A successful command alone is not an AC decision. A user may explicitly record criterion-level risk acceptance, but it stays marked as risk acceptance rather than pass. An approved Review's advisory issue blocks final acceptance until the Owner either gets a new clean Review or explicitly waives that exact current issue and attests it is not a security, privacy, credential or data-loss issue. The immutable waiver records issue ID/revision, Review ID, snapshot, reason, actor and time; the issue is shown `waived`, never `pass`. A blocking Review or failed check cannot be waived through this path. The Host records `actor=local-owner` from its current local trust context, never from Renderer payload. Later remote principals need their own authenticated adapter and policy.

SQLite migration v21 appends immutable, idempotent `final_acceptance_decisions` with snapshot/Contract/basis/actor/reason and an optional reserved next Run ID for an explicit human return, plus immutable `review_advisory_waivers`. It does not rebuild the historical `tasks` table, whose frozen v8 CHECK allows only `todo`. The Board projects `Done` only from a current accepted final decision; a new snapshot invalidates old acceptance. Done does not merge, push, publish or deploy. This additive projection preserves existing Project/Task/Run rows and legacy migration checksums.

The Owner may return the current delivered snapshot with feedback. The Host records the decision first and then starts a new owned Developer Run/Attempt from that snapshot's checked Git ref, frozen RunConfig and current Environment. Feedback is bounded, redacted and tagged as a human decision in ContextBundle. An unavailable Executor leaves the durable return visible as `RETURN_ATTEMPT_NOT_STARTED`; replaying the same idempotency key may retry the same reserved Run ID without creating a second writer. A new Handoff requires fresh Review, Verify, criterion decisions and final acceptance. The global twenty-attempt ceiling applies before reserving a human return. This is a bounded one-node development continuation, not a Workflow Engine.

## Evidence and limits

Disposable Git/SQLite/owned-process tests verify hard-gate refusal, explicit per-AC evidence and approved Review, report-change CAS rejection, accepted decision persistence/restart, Board Done projection without source mutation, human return to new Attempt and new snapshot invalidation. Component and TypeScript contract tests verify explicit confirmation, stale-state error and the fixed bridge. Authenticated Electron→Python Host→Codex development, Verify, Review and final Owner acceptance passed in a disposable repository; the visible Board projected Done without source mutation. The actual screenshot is `output/playwright/p3-07-python-desktop-accepted-1440x900.png`. The full quality chain and concrete IDs are in implementation status.

The Review issue schema does not reliably classify a blocking finding as security or non-security. Final acceptance therefore does not waive a blocking Review. The explicit Owner waiver applies only to Reviewer suggestions from an approved Review and remains separate from an AC `risk_accepted` decision. A real Codex run returning an advisory suggestion and subsequent Owner waiver has not been forced; the real Host/Git/SQLite structured fixture covers this path. Current user database upgrade, Windows x64, macOS Intel and installer packaging remain unverified.
