# ADR 0044 · Host startup recovery and side-effect reconciliation

Date: 2026-09-24<br>
Status: Accepted for P3-09 on the Python Core path

## Decision

Python Host performs recovery on the first writable storage handshake, before admitting new Run commands. It reads durable Run/Attempt/lease records and the prior runtime's process journal. Every prior `queued`, `running`, `pausing` or `canceling` Run with an active Attempt becomes `interrupted`; an active workspace lease becomes `quarantined`. The original Attempt identity, lease epoch, provider session reference, snapshot/diff evidence and audit history remain. Recovery writes a `host_restart_outcome_unknown` audit event and is idempotent on later handshakes. A historical PID and Forge spawn timestamp do not establish current kernel process identity: PID reuse and lost parent ownership make automatic signals or adoption unsafe. A provider session reference alone does not prove the workspace and process can be safely resumed. This version does not auto-resume or auto-restart the Executor; the user must inspect the interrupted Run and initiate a new explicit action. The quarantined lease blocks another writer until ownership is actually reconciled. Terminal Runs are untouched.

The Host audits every unresolved local merge operation intent at startup, without running Git merge. If the target branch commit is the exact two-parent result of the recorded base and snapshot **and** the Forge-owned candidate worktree still points to that same commit and common Git directory, the same operation is marked `merged`. Matching parents alone are insufficient because an external writer could create a different tree. If the target branch still equals the recorded base, the intent remains pending with `MERGE_RETRY_REQUIRES_CONFIRMATION`; the UI states that human reconciliation is required and offers no new merge key. An unexpected commit or absent/mismatched candidate is `unknown`; an inaccessible repository leaves the intent intact for investigation. No force update, reset, prune, process-name kill, push or deploy occurs. Git and SQLite cannot commit atomically, so an explicit durable intent plus target commit/parent/candidate comparison is the recovery boundary. An existing key may be retried only by a new explicit caller action; startup never does so.

Review, Verify and Rework jobs retain their existing conservative interrupted-on-restart behavior. Normal cancellation still releases a lease only after owned process-tree exit is confirmed; otherwise it quarantines. Finite 429 retry remains limited to a provider error that explicitly guarantees no side effect. Duplicate terminal results and old-epoch results remain fenced and audited by RunService. `reconcile_required` is an interruption reason, not a new public Run state.

## Evidence and limits

Independent process crash injection (`os._exit`, without graceful cleanup) on isolated accepted Git/SQLite fixtures covers (1) durable merge intent before Git side effect, (2) candidate two-parent commit before target update, and (3) target update before receipt. A fourth case removes candidate evidence after target update: startup marks the outcome unknown instead of guessing success. New Host startup never replays merge; it leaves the first two pending and recognizes the third exact result. The target branch has one merge commit with recorded parents and a clean source checkout. A separate Run fixture proves startup fences an unfinished Attempt, retains its lease and never signals even a historical journal entry that claims the test process PID; a second restart does not reapply recovery. Run result replay and stale epoch tests cover T031/T032. Existing scheduler and owned-process tests cover bounded no-side-effect 429 (T033) and confirmed cancellation/quarantine (T035). T034's Host-death merge boundary is exercised here; the prior deferred entries can be closed.

This does not claim safe automatic cleanup of a still-running orphan process, native Codex session reattachment, Windows/Intel behavior, installed-bundle paths or recovery after concurrent external Git writes. Those remain diagnostics/manual work. Python Core stays the only business runtime; Renderer/Main never inspect PIDs, SQLite or Git directly. No schema or dependency change and no user database reset.

For Desktop data-profile switching, a malformed or torn process journal entry is also unresolved ownership evidence. The Host counts those entries separately from valid prior-runtime records and conservatively refuses switching profiles. It does not infer a live PID or clean the journal merely to make a data switch pass; see ADR 0083. This extends the recovery fence without changing the Run state machine or granting a new cleanup command.

## Desktop capability projection · 2026-09-26

The follow-up read-only preview described below preserves this gate; it never releases a quarantined lease.

An interrupted Run or quarantined workspace lease now makes the same Project's `run.capabilities` unavailable with `RUN_RECOVERY_REQUIRED`; `run.start` checks the fence before creating a new workspace. The Task drawer explains that the interrupted record is not success and will not be retried or cleaned automatically. A copied SQLite database from an actually crashed installed Codex Run was opened by a newer installed Desktop and displayed this state; no new model call was made. This does not provide a reconciliation command. Codex child commands can use a different process group from the app-server, so loss of the old app-server PID alone cannot prove the old workspace has no writer. A future explicit user recovery path must establish process and workspace safety before releasing the quarantined lease; a historical PID, directory name, or UI confirmation alone is insufficient. Existing Run, lease and audit data remain intact.

## Read-only quarantined worktree preview · 2026-09-26

For an `interrupted` Run with a `quarantined` lease, the Host can now verify the matching historical workspace ownership record and Git worktree identity, then return a bounded redacted Diff of the **currently existing** worktree. This is a viewing operation only. The returned basis is `live-worktree-unverified`, separate from immutable CodeSnapshot and Review evidence; it does not prove that a former Codex child is gone or that the tree will stop changing. Missing, symlinked or mismatched ownership evidence fails closed with `RUN_RECOVERY_EVIDENCE_INVALID`. A copied SQLite database without its historical worktree was tested in an installed app and rejected. No previous-runtime process is adopted, signaled or cleaned, and no quarantined lease is released. The recovery/start gate above remains in force.

## Project archive safety fence · 2026-09-27

`project.remove` is a metadata archive. Removing trust and the active Project context while a writer is running would leave that writer without a visible Project. The Host now checks the archive in the same SQLite transaction as the Project revision update. An active Run or lease, Review, Verify, rework launch, or unresolved merge returns `PROJECT_BUSY`; an interrupted Run or quarantined lease returns the existing `RUN_RECOVERY_REQUIRED`. The transaction rolls back the Project revision, archive time, and active selection on either error. A completed Project can still be removed without deleting its Git tree. Checks for later job tables depend on the installed schema version so old version 15 Project stores retain their original removal behavior. This adds one error code to current protocol v5, with no migration, remote write method, process signal, lease release, or new permission.

An interrupted Review or Verify is also unresolved work, even if the Run itself is terminal. The same archive transaction therefore returns `RUN_RECOVERY_REQUIRED` for those durable jobs on schema versions that contain their tables. This closes the path where removing a Project hid an interrupted reviewer or verifier from its normal Desktop context; it does not claim the historical child process has exited or release its evidence. Older schema 15 retains its prior conditional checks.

### Final intent interlock · 2026-09-27

Async workspace and Review-copy preparation creates a window before a Run/Job exists for the archive transaction to see. Developer Run, Review and Verify therefore recheck the current trusted, non-archived Project inside their final SQLite intent transaction. If archive or Project switch wins during preparation, the new intent is rejected and disposable resources are released; if the intent wins first, the existing archive fence sees its active record. A real verifier process and a paused worktree-creation fixture exercise both orderings. This does not infer process identity from stale PIDs or release quarantined workspaces. No protocol, schema, permission or dependency changes are needed.
