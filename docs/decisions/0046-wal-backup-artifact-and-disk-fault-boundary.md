# ADR 0046 · WAL backup, artifact import and disk-fault boundary

Date: 2026-09-24  
Status: Accepted for P3-11 on the Python Core path

## Decision

The Python Host remains the sole SQLite writer. `ForgePersistence.backup()` uses SQLite's online backup API on its live connection, validates quick check and foreign keys, then atomically publishes a version-labelled private copy. It never copies only `forge.sqlite` while WAL is active. Before upgrading an existing schema, `migrate()` checks conservative free space and creates this backup before the first DDL step. A fresh empty database needs no pre-migration copy. Migration v24 is additive; legacy migrations and checksums are unchanged. A failing migration rolls back its current SQLite transaction, leaves the pre-upgrade backup and old records in place, latches storage unavailable for writes and exposes a path-free diagnostic. Restore is an explicit, separate recovery operation, not an automatic overwrite of a possibly newer user database.

SQLite `FULL`, I/O, read-only or corrupt write errors are mapped to distinct storage diagnostics; `FULL` latches `DATABASE_DISK_FULL`. Further writes are rejected until the Host is restarted after the underlying problem is resolved. Reads remain available to diagnostic code; system health reports degraded. SQLite constraint failures remain constraint failures and do not falsely mark the database as broken. Backup files live only under Forge's own data directory with private directory/file permissions on POSIX. Host does not log backup paths, credentials or complete environment variables.

The small generic `ArtifactStore` accepts only UTF-8 text/plain or application/json reports from an existing, project-matched Verifier job's Forge-owned workspace. It rejects absolute/traversal paths, symlink components, wrong MIME/suffix, oversized or obviously sensitive content. It stores at most 1 MiB per item as immutable SQLite BLOB with project/job identity and digest, so a SQLite backup includes the imported evidence. It does not accept arbitrary Renderer paths, external web URLs or JavaScript MIME. This adds an import boundary; the current verifier still captures its ordinary stdout/stderr in its existing SQLite evidence table.

`PluginStorage` offers only bounded JSON get/put under a fixed plugin namespace. The Host registers a broker; `PluginContext.require_service("storage.v1")` returns only the requesting manifest's scoped handle when declared, never the broker or SQL session. The built-in Codex plugin does not request storage. T090 covers this storage-interface boundary: the handle has no SQL/query method and cannot use it to read a Core table. This API is not a Python language or OS sandbox. A malicious third-party plugin using reflection or direct disk access requires P4 plugin isolation and remains unverified; it is outside the stated T090 interface test.

## Evidence and limits

Disposable SQLite/Git tests inject a real process exit midway through approval/Task/event writes and confirm no half commit; backup an active WAL database with an approved Task and imported Artifact, restore it, and pass foreign-key check; perform an independent Python Host schema23→24 startup with a v23 backup; inject bad migration SQL and confirm old data plus read-only diagnostics; force genuine SQLite `FULL` through `max_page_count` and confirm rollback/health error. Artifact tests exercise traversal, symlink, wrong MIME, foreign project/job and successful content read. Plugin tests exercise the manifest-scoped service, Core SQL interface denial and different plugin namespaces. T057's external report path/MIME guard is exercised at the actual import service. SQLite backup contains metadata and stored artifacts, but does not back up external Git CodeSnapshot objects or user project repositories. Existing user databases, packaged runtime, Windows x64 and macOS Intel remain unverified.
