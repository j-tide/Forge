# ADR 0067 · Published linear Workflow runtime and retrieval freeze

Status: Accepted for P5-11 development scope on macOS arm64, 2026-09-25.

The Python Host may execute a published custom Workflow only when its compiled definition exactly matches the supported quick chain: Develop → Review → Verify → human owner acceptance. Node labels and bound Developer/Reviewer Profiles may differ; node semantics, routes, retry/rework limits, outputs and budgets may not. Planner, conditions, arbitrary commands and other graph shapes fail closed at launch. Publication is a static validation step, not permission to run every published graph. Each stage remains an explicit user/API action with real evidence; no hidden automatic Review, Verify or owner acceptance is claimed. This narrow admission reuses the existing P3 Run/Review/Verifier/final-decision services in the Python Host rather than creating a second state machine. Main and Renderer do not dispatch stages.

The approved Task's Workflow reference and the exact published revision/content hash are frozen in RunConfig. The Developer Profile and the Reviewer Profile version/hash are frozen separately. Review checks the frozen Reviewer lock and read-only capability. Verify rejects a Project Command preset exceeding the published Verify time budget. Rework and human return count real Development/Review/Verify attempts against the frozen Workflow's 16-attempt limit (and the existing 20-attempt Host ceiling); the three-cycle limit remains. A duplicate start returns the original Run even after TODO has advanced, provided the request matches its immutable config. A later Workflow/Profile publication affects only later Runs after an explicit Task revision change.

When a launch includes a retrieval query, the Host builds Stage Context from the approved Task and current Project/environment sources. Conflict or no answer blocks launch; neither is converted into an invented answer. Only bounded, explicitly tagged knowledge or validated-memory items enter the immutable ContextBundle. Retrieved project text is `untrusted_project`; validated memory remains guidance, not acceptance authority. The historical bundle is never rewritten on source revocation. A fixed read-only `context.sources` command compares each frozen source with current source version/status/hash and reports current, revoked, superseded, expired or missing. `run.config` exposes sanitized frozen identities and actual node ID; no raw provider payload, database path or arbitrary Host method is exposed to Renderer.

Real Electron/Python Host/Codex fixture evidence: a published four-stage custom chain reached a CodeSnapshot, independent Verify pass, read-only Review approval and explicit owner acceptance; the source Git tree remained clean. A second real fixture rejected no-answer and conflicting sources, froze a knowledge citation in a completed Codex Run, then showed that citation revoked in Desktop while preserving historical Run input. The same repository can change Workflow/Profile only through approved Task revision, with old/new RunConfig hashes retained in SQLite. A real SQLite/Verifier fixture exhausted the custom 16-attempt budget and produced a blocked rework cycle with no next Run. Generic P3 duplicate/epoch/429/crash/cancel safeguards continue to own the shared scheduler and process path. These results cover one real Codex Executor only; Claude and full P4 multi-Executor release remain blocked. T116–T120 eval and cross-role total-cost cases remain assigned to their later authoritative owners. Windows, macOS Intel, installer, real user database upgrade and non-linear Workflow execution are unverified or unsupported.
