# ADR 0073 — Internal macOS package and distribution gate

Date: 2026-09-25
Status: Internal package implemented; P6-06 distribution acceptance blocked

## Decision

Forge's macOS Desktop bundle contains a production Web build, the Desktop Main/Preload in `app.asar`, and an independent Python 3.12.13 Host under `Contents/Resources/forge-python`. Main resolves these paths from the bundle and provides only fixed `PYTHONHOME` and `PYTHONPATH` to its owned Host. Development still uses the workspace `.venv`; the two paths are explicit. SQLite remains Host-owned in Forge Application Support. This package does not migrate or delete an existing database.

`pnpm package:mac:internal` uses the frozen pnpm and uv locks, `pnpm deploy --prod --offline --node-linker=hoisted`, a wheel built from current `python/`, locked production wheels, and Electron 44.4.3. The internal `.app` is ad-hoc signed and wrapped in a DMG marked **INTERNAL / ADHOC / UNNOTARIZED**. It is not a Developer ID signature, a notarization, a Gatekeeper-distributable release, or an upgrade mechanism. The bundle includes an internal-test marker solely to redirect app data to an isolated QA directory when explicitly requested by the smoke script. Public packages must omit this marker.

The internal package uses `@electron/asar@4.3.0` (MIT, Node >=22.12; exact root dev dependency). The locked runtime Python build comes from uv's managed CPython 3.12.13; the local `.venv` symlink itself is not copied. The locked Claude SDK may be present as an inert dependency; no Claude authentication or model call is made. A Codex CLI installation and authorization are not bundled or claimed available for a newly installed user.

## Evidence and limits

On macOS arm64, `hdiutil verify`, `codesign --verify --deep --strict`, the bundled Python/SQLite import probe and the isolated DMG mount/copy/launch smoke pass. The copied app runs from a path containing spaces, Electron reports `app.isPackaged=true`, Renderer retains sandbox/context isolation/Node disabled, and the bundled Host reports real health with SQLite schema 30. The smoke redirects only its internal artifact to a disposable user data root and checks the installed app can be removed while the database remains. It does not use the developer `.venv` or touch the current user's Forge development database.

An early smoke attempt used only `HOME` for isolation; macOS Electron kept its default `@forge/desktop` Chromium cache under the actual user. That pre-existing user data directory was left intact, and no `Forge/production` database was observed. The passing smoke explicitly redirects `appData` and `userData` only when the internal-build marker and test path are both present. Copying the app to a macOS temporary directory caused a sandbox-extension denial; the passing QA install is a separate `build/macos/qa-install-*` directory with isolated data. This is not a fresh physical Mac account or Gatekeeper test.

The machine has an Apple Development identity but no observed **Developer ID Application** identity or notarization credential. [Electron's signing guide](https://www.electronjs.org/docs/latest/tutorial/code-signing) requires code signing and Apple notarization for macOS distribution; its [Mac App Store guide](https://www.electronjs.org/docs/latest/tutorial/mac-app-store-submission-guide) distinguishes Apple Development from Developer ID Application outside the store. The [Electron distribution guide](https://www.electronjs.org/docs/latest/tutorial/application-distribution) documents `app.asar` and macOS bundle rebranding. [uv documents managed Python builds](https://docs.astral.sh/uv/concepts/python-versions/) and [virtual environment relocation limits](https://docs.astral.sh/uv/reference/storage/). References checked 2026-09-25.

The ad-hoc artifact does not establish T111's public Gatekeeper install. T112's signed upgrade/rollback and T113's credential continuity require a later real signed update and authorized test credential. macOS x64, fresh physical Mac user, Gatekeeper on an unconfigured Mac, code signing with Developer ID, notarization, CI release, Codex from Finder PATH and Windows remain **UNVERIFIED**. P6-06 is therefore **BLOCKED**, not DONE; P6-07 keeps its canonical dependency. An Apple Developer Program account/Developer ID and notary credentials or an explicitly authorized narrow development scheduling exception are needed before moving beyond this dependency. No public release or signing claim follows from this internal artifact.

## Authorized development scheduling exception · 2026-09-25

The user subsequently approved the exact `P6-06 → P6-07` development edge. The mounted/copied internal arm64 package, bundled Host and isolated-data smoke are the prerequisite evidence; the same artifact's product workflow must be checked before P6-07 work proceeds. This exception changes scheduling only. P6-06 remains **BLOCKED**, T111–T113 remain **DEFERRED_VERIFICATION**, and Developer ID signing, notarization, Mac x64, a fresh Gatekeeper user, signed upgrade/rollback and credential continuity remain unverified. Windows preparation can proceed independently; Windows support and P6 release acceptance require a real installed Windows x64 task and signing/UAC evidence. Later P6 edges require their own exact records and checks. No public upload or release is authorized.
