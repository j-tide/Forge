# ADR 0079 — Remote command adapter and write gate

Status: Accepted for the P7-05 development probe (2026-09-25). P7-05 remains BLOCKED for its full public write set and remote acceptance.

## 2026-09-26 two-device approval contention probe

A separate, isolated Host/SQLite/loopback HTTP fixture now pairs **two distinct devices** with the same Project and `task:approve` grant. Both submit different command IDs and idempotency keys for one live Approval concurrently. Exactly one receives `200` and creates the TODO; the other receives `409 REMOTE_APPROVAL_STALE`. The winner's exact retry returns its original receipt. The other device cannot read that receipt, and its failed command has no receipt. SQLite contains exactly one Task, one matching remote command receipt and zero Runs. This strengthens the local freshness and idempotency evidence; it does not implement remote rejection, prove a physical two-phone race, or clear P7-05/P7-09/P8 Gate.

## 2026-09-25 receipt authorization recheck

A completed remote command receipt may contain message or Draft data. Looking it up by the original device ID and a still-granted Project was insufficient after that device's operation scope was narrowed. Receipt reads now recheck the **current** Host-owned scope for the stored command method. A device that retains Project read access but loses `task:draft` cannot fetch its old message receipt; another device still receives 404. Real Host-restart/SQLite and authenticated loopback HTTP tests cover the scoped denial. This does not delete the durable receipt or grant a new write.

## 2026-09-25 concurrent Draft revision evidence

Two distinct authenticated `tasks.revise` HTTP requests were submitted concurrently with the same Draft revision and distinct decision IDs. The single Python Host/SQLite writer committed one revision and one device receipt; the other returned `DRAFT_INVALID_REVISION` (409), with no overwrite or receipt. This proves CAS for the presently supported manual Draft revision path. T093 remains deferred for the full remote Task/mobile scenario and does not authorize additional write methods.

## 2026-09-25 bounded conversation history read

The fixed `GET /v1/projects/{projectId}/conversations/{conversationId}/messages` path is a separate read projection for P8-06. It rechecks the authenticated device's current Project and `task:draft` operation grant, resolves the conversation in Host storage, and uses sequence-keyset pagination. Only user/assistant text crosses the boundary: at most 20 messages per page, 4000 characters each with an explicit truncation flag. System/tool bodies and attachments remain Host-side. The browser renders returned text without HTML interpretation, keeps it in memory only, and clears it when its device/Project/conversation/connection changes. This does not add a remote model call or widen the public command whitelist. Real loopback Host/SQLite and built Chromium evidence is recorded in the implementation status; private HTTPS/physical phone remain unverified.

## 2026-09-25 P8-06 source-bound manual draft and narrow revision

The public `tasks.createDraft` body carries a complete Task Contract but no separate conversation or decision fields. The mobile UI requires a message it has just saved through the Host and a user-filled Contract. It places the **real** `message:<UUID>` and the explicit user action's `decision:<commandId>` in the Contract's source references. Under the same SQLite transaction as the device-scoped receipt, the Host rechecks session, CSRF, current Project/`task:draft` grant, exact source references, and that the completed user message belongs to an unarchived conversation in that Project. The Host obtains the conversation from its own row. It creates one proposed or needs-clarification Draft with revision history; it does not create a TODO, start a Run, or invoke a model. Same-command retry returns the prior receipt; different content or duplicate source cannot silently create another Draft.

For `tasks.revise`, the public `reason` is the user's revision summary and the UUID command ID is its decision ID. The candidate Contract must retain all previous source references and add that decision reference; the existing DraftService checks the expected revision and acceptance provenance. The Host commits the revision and remote receipt atomically. Because the public body has no resolved-question answers, acceptance-removal confirmation or scope-change confirmation, this adapter **rejects** removal of open questions/acceptance criteria and scope changes. It never sets these missing acknowledgements to true. The mobile form can revise bounded title, goal, first acceptance statement, type, priority and workflow. A fixed `GET /v1/projects/{projectId}/conversations/{conversationId}/drafts` reads only the current Project/conversation's bounded Draft projection after the Host rechecks the device's `task:draft` operation grant. Its row cursor is keyset bounded; it excludes original source text, local paths and model internals, and marks approved drafts noneditable. A page reload can explicitly reread and review an unapproved Host Draft before CAS revision; Desktop remains the complete revision surface.

The exact write set is now `conversations.send`, source-bound `tasks.createDraft`, narrow `tasks.revise`, and approve-only `tasks.approve`, each conditional on current Host grants. Other public writes remain denied. Browser evidence is a built Vue 390×844 page against a disposable loopback Python Host/SQLite: one user message, one Draft, two immutable revisions, zero Tasks, zero Runs, plus page reload→Host Draft list→explicit revision-2 receipt. The pairing approval was performed by an explicit fixture controller. This is not private HTTPS, physical-phone or installed-app acceptance, and it does not complete T091–T093 or P7-05.

## 2026-09-25 P8-05 approve-only mobile boundary

The mobile Inbox reads a fresh, closed Task approval detail from the authenticated Host, including the current Contract, revision, scope hash, action digest, expiry, operation grant, required approval effect, and null code snapshot for a draft. The URL is a fixed read route; Host searches only the paired device's currently granted Projects, verifies its `task:approve` grant and live Draft/Approval equality, and returns 404 for absent/out-of-scope approvals and 409 for stale ones. This is a production additive projection because the reference OpenAPI approval list lacks a detail response schema; the read-only baseline is unchanged.

The UI rereads before opening the deliberate confirmation and again before POST. A changed fingerprint forces review instead of retaining confirmation. Only the versioned `tasks.approve` envelope, CSRF token and Project-granted session reach the existing Host transaction. A double tap creates one client command; the Host remains the authority for idempotency and atomic TODO creation. An uncertain network response is never treated as success or replayed automatically; the user may explicitly query the same command receipt. The mobile screen has no arbitrary command builder, local file access, or offline write queue.

This does **not** authorize remote rejection or other dangerous commands. The canonical command registry exposes approve-only `tasks.approve`, while local `approvals.decide` supports both approve and reject and is marked `remoteAllowed: false`; T103's two-device approve/reject wording therefore needs a later explicit public-command decision before a mobile reject path exists. `runs.start/pause/resume/cancel` and `acceptance.decide` still fail closed at P7-05. Browser evidence uses disposable loopback Host/SQLite with the fixture controller explicitly approving pairing; private HTTPS, physical phone and same-Desktop pairing are not inferred.

## 2026-09-25 P8-04 read-only Task evidence and Diff

The mobile Task page uses the existing authenticated Project grant. Its fixed Task detail, activity and Diff endpoints search only authorized Projects; an absent or out-of-scope Task has the same 404. Evidence is limited to IDs, statuses, snapshot IDs and timestamps from existing Review, Verify, Owner and Delivery tables. It never returns full reports, command output, user file paths or a local artifact endpoint. The page labels these records as historical, since a later snapshot can invalidate an earlier decision.

Diff text comes only from the Host's persisted bounded preview, not a mobile-requested workspace path. New captures reject hidden paths, common credential filenames, private-key formats, traversal and escaping links; known secret patterns are redacted. The remote reader rechecks stored paths, returns no text when the latest Run has no shareable files, and binds page cursors to the exact preview hash. This is conservative filtering rather than a claim to recognize every secret embedded in otherwise ordinary source text. Current private HTTPS/phone security acceptance remains blocked; normal Desktop does not start the gateway.

## 2026-09-25 production read projection for P8-03

The running Host Board has a real `blocked` Task state that the read-only reference OpenAPI `TaskSummary.state` omits. P8-03 keeps `blocked` in a separately versioned production Zod projection and never maps it to `active` or `done`; the untouched reference file remains a known contract discrepancy. The reference `/v1/approvals` also has no response schema, so the running endpoint returns only current, freshness-checked Task approval summaries, with a Host row cursor; it does not imply permission to decide them. A new additive `GET /v1/projects/{id}/tasks` produces a bounded page derived from the same Host Board snapshot with a cursor tied to `boardRevision`, returning 409 after revision changes. The gateway and Host recheck the current authenticated Project grant; unpaired Web gets no data. The mobile client uses fixed same-origin paths, strict response schemas and only an in-memory stale read view after disconnection. No reference contracts were silently edited, and this does not authorize any new write or listener. The current Board does not yet produce `awaiting_acceptance`; complete owner-action listing remains P8-05 work.

## 2026-09-25 exact remote task approval

`tasks.approve` is an approve-only public method: the versioned envelope supplies `expectedRevision`, the closed body supplies `approvalId` and `scopeHash`, and `resourceId`, when present, must match that Approval ID. The existing local approve path uses `decision="approve"` and an empty reason; a reason is required only for rejection. No task revision, digest, snapshot or actor is invented from client input. Under the same SQLite write transaction, the Host reauthenticates the session and CSRF token, rechecks the paired device's current Project and `task:approve` grant, returns an exact prior device-scoped receipt if present, verifies the live Approval/Draft revision, scope hash, action digest and expiry, invokes the existing Approval Service, creates the TODO and persists a minimal receipt. A different request using the same command ID or idempotency key fails 409. After the first approval, another device's fresh command fails 409; it cannot create a second TODO. Narrowing or revoking the device prevents subsequent requests, including receipt replay.

This is real isolated Host/SQLite and loopback HTTP evidence, with no model call and no public listener. It does not complete `tasks.revise`, `runs.start/pause/resume/cancel`, `acceptance.decide`, private HTTPS or a physical phone. T091–T093 retain their full deferred verification: one positive approval path and a two-device sequential race do not prove every public write or a true simultaneous Task revision race. The paragraphs below preserve earlier checkpoints and must not be read as the current write whitelist.

## 2026-09-25 narrow positive write and durable receipt (historical checkpoint)

The only lossless public write currently enabled in the optional loopback adapter is `conversations.send` with empty `attachmentIds`. A Host-owned paired-device session must carry the exact Project and `task:draft` grant. The Host rechecks session, CSRF and grant inside the SQLite write transaction. Schema 34→35 adds `remote_command_receipts`; receipt insertion, message append, conversation revision CAS and minimal SSE invalidation commit together. The original `commandId` and receipt survive Host restart; a retry with the same device/key/body returns the original receipt, while changed content or command-ID reuse returns 409. The existing local Conversation Service performs the write; its idempotency key is partitioned by authenticated device before use so two devices cannot mistake one another's message for a retry. `GET /v1/commands/{commandId}` retrieves only the same device's receipt while its Project grant is still current. This permits a client to check an uncertain response instead of replaying an offline decision.

The Host has no attachment storage for this message operation, so nonempty `attachmentIds` return 422 rather than acknowledging discarded data. `replyStatus=unavailable` remains honest: saving a message does not imply a model reply or Task creation. No other public write is enabled. In particular, `tasks.approve` still lacks a decision/reason and atomic approval mapping; Task CAS concurrency T093, positive Run commands and final acceptance remain open. P7-05 as a whole stays BLOCKED. This additive database migration was tested on isolated data; an existing user's database upgrade and a newly packaged app remain unverified.

## 2026-09-25 implementation reconciliation

The user has now authorized the minimum safe, reversible contract mapping without relaxing the write gate. The production adapter validates the public `conversations.send` body as a closed schema, verifies its Project and optional resource identity, and constructs a typed `conversation.send` Host invocation while retaining the caller's expected revision and idempotency key. Constructing this mapping has no side effect and does not dispatch it. Missing or forged fields are rejected; all valid remote writes still return 403 because the paired device has no operation grant. Other public methods remain explicitly unmapped until their required Task revision, decision reason, snapshot/basis and provider configuration can be obtained from real Host state or the contract is reconciled. No value is invented to satisfy a local input model.

Real loopback HTTP and unit tests cover valid mapping, malformed body, conflicting resource ID, unsupported mapping, actor forgery and continued write denial. Positive T091–T093, T094 SSE and P7-05 completion remain open. The former A/B request is superseded by this minimum safe decision; subsequent independent work may proceed only through an exact development dependency exception, never by treating P7-05 as DONE.

## Decision

The optional loopback gateway now serves authenticated `GET /v1/projects`, `GET /v1/projects/{projectId}/board`, and `GET /v1/tasks/{taskId}`. All go through the Python Host's existing JSON-RPC CommandBus after the Host checks the current session and its persisted Project allowlist. Because the public task URL does not contain a Project ID, the adapter searches only the session's granted Projects and gives the same 404 for an absent or unauthorized task. It strips local paths, source text, and local-only allowed commands from the public projection. The ordinary static gateway and Desktop startup still do not start an authenticated HTTP listener.

`POST /v1/commands` accepts only the versioned, closed command envelope from the reference OpenAPI. The Host derives identity from its session, requires CSRF, rejects client actor/scopes, and rejects unknown or local-only methods before Host dispatch. All planned remote writes currently return `REMOTE_WRITE_SCOPE_UNAVAILABLE` (403). Project approval at pairing is a data-access grant, not an operation grant. P7-07 must add explicit operation scope and freshness checks before any write may be routed. No UI or caller may treat this 403 as a successful command.

## Contract reconciliation

The reference `planning/commands.json` names permitted HTTP write methods such as `conversations.send` and `tasks.approve`; the running Python Host uses different local methods and payload models, including `conversation.send` and `approval.decide`. A silent string rename would bypass the needed payload, actor, CAS and idempotency translation. P7-05 must complete that mapping against the same Host service and real write tests before its implementation can be marked DONE. T091–T093 remain unexecuted for successful remote writes; T094 belongs to P7-06 SSE cursor handling. T095's unknown-command denial has real loopback evidence.

The mismatch is concrete: `conversations.send` can map its body plus envelope Project/idempotency key into `conversation.send`, but local `ConversationSend` does not yet accept the envelope's `expectedRevision`. `tasks.createDraft` has a contract body while the local `draft.manual` requires a conversation and source message. `tasks.approve` lacks the local decision's revision/reason fields. `runs.start` supplies workflow/environment but the local launch requires an explicit model and task revision; `runs.pause`/`runs.resume` have no equivalent in the current Python Host. `runs.cancel` carries a reason that the local cancellation path does not record. `acceptance.decide` has a scope hash/snapshot but the local final acceptance requires a current basis hash and contract revision. These cannot be treated as equivalent by renaming methods or inventing missing audit values.

There is also a task-order dependency: pairing currently grants read access to named Projects, not permission to mutate conversations, tasks or Runs. P7-07 owns device operation grants and approval freshness, yet P7-05's successful write-path T091–T093 require at least a narrow grant. The two safe implementation choices differ in authoritative Task scope: (a) keep P7-05 in progress and bring forward a minimal, explicitly approved operation grant plus versioned command translation, with P7-07 retaining full freshness/scope policy; or (b) close P7-05 only for read/deny and defer positive writes to P7-07 under an explicit task-scope reconciliation. No change to the read-only reference contracts or reduction of the security gate is implied by either choice. Until that scope decision, the only production behavior is deny-all remote writes.

The reference OpenAPI `TaskSummary.state` omits the production `blocked` state. The adapter currently refuses a board containing such a task with `REMOTE_SCHEMA_UNSUPPORTED` (409), instead of misrepresenting it as active or done. Production Project `defaultBranch` can be unknown/null while OpenAPI requires a string; the adapter emits the literal `unknown`, matching the existing product UI language. Neither reference contract is modified here. The blocked-state discrepancy requires an explicit contract decision before full remote board acceptance.

## Evidence and limits

Real loopback HTTP with a live Python Host/SQLite exercises session-bound Project filtering, path minimization, valid board and approved Task Contract read, absent-task denial, forbidden Project, malformed query, cross-origin/CSRF denial, actor forgery, unknown methods, planned-write 403 and immediate denial after revoke. The command body has a bounded 64 KiB ingress limit, while pairing metadata keeps the smaller 4 KiB limit. This is development-only loopback evidence, not private HTTPS or phone evidence. No external network port, paid provider call, desktop release or P6/P7 gate is enabled by this ADR.
