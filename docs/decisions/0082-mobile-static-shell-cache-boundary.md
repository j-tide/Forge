# ADR 0082 · Mobile static shell cache boundary

Status: Accepted for the current P8-07 development slice, 2026-09-25.

## 2026-09-26 session-bound Host text addendum

The offline user-authored message text remains separate from Host-provided conversation history. The mobile view now keys Host conversation/message/Draft reads to the Project, device and current session ID. Loss or rotation of that session immediately removes Host text and fences responses from the old session. When the same device reconnects, unsent local text may remain in its input, but a missing former conversation leaves no send target; the user must select a new conversation deliberately. This is a client defense in addition to Host authorization, not a claim that sessionStorage is a secure vault or that a remote command may be replayed.

## Decision

The built Vue mobile route may register one versioned Service Worker on an authenticated same-origin gateway served over HTTPS or local loopback. The worker precaches only the build's fixed HTML, hashed JavaScript/CSS, manifest, and Forge icons. Navigation to `/` or `/index.html` tries the network first, then the cached static HTML. It never intercepts `/v1` Host API requests, writes, evidence downloads, arbitrary files, or cross-origin requests. The gateway allows only these named static files and its existing hashed asset directory.

The cache name is scoped to `forge-shell-` and the current build asset list. A separate, versioned localStorage record may hold only the last confirmed counts of viewed projects, tasks, pending approvals and blocked tasks, a partial-page bit, device identity and timestamps. It contains no titles, IDs of projects/tasks, contract text, source, paths, evidence, code, tokens or commands. It expires no later than the session or 24 hours, whichever comes first. Offline display labels it stale and disables every Host operation. The account page offers an explicit clear action that deletes only Forge's shell cache, redacted record and worker registration. Local session revocation does the same. Host project, task, approval and SQLite data are never stored in this browser cache or deleted by this action. A remote revocation while the browser is offline cannot forcibly clear a remote device's local cache; the next online session check detects `REMOTE_AUTH_REVOKED` and removes both Forge caches.

## Limits and evidence

P8-06 adds one **explicitly saved, tab-scoped** unsent message draft in `sessionStorage`, separate from the redacted `localStorage` counts above. It contains user-authored text plus device/Project/conversation identity and saved/expiry times, so it is treated as sensitive browser-local content, not as an offline Host record. It is bounded to 30,000 characters and expires no later than the verified session or 24 hours; an offline edit cannot extend expiry. A different authenticated device or lost Project grant cannot adopt it. The user can clear it; local disconnect/cache clearing and detected Host revocation clear it as well. No Service Worker API intercept, background sync, command object, approval, Start or automatic replay is stored. A browser/tab compromise can read its text; physical-device and private-HTTPS behavior remains unverified.

This is a local-browser PWA/cache slice. Reopening an already saved Host Draft for further mobile revision has since passed a separate built-Vue/loopback-Host browser check after page reload; private HTTPS and physical-phone installation/revocation tests remain open. Offline Host status and all operations show unavailable; no command queue or automatic replay exists. A real authenticated loopback Host/SQLite browser test confirmed a fresh redacted summary after page reload while offline, then Desktop-equivalent Host policy revocation caused browser cache/summary removal on the next online check. The temporary Host DB still held one Project and one Task. The build test checks manifest/icon files and executes the generated worker to assert that Host API GETs and POSTs are unhandled. P8-07 remains IN_PROGRESS and does not pass the P8 release gate.

The manifest and worker setup follow the [Chrome installability guidance](https://developer.chrome.com/docs/lighthouse/pwa/installable-manifest) and [web.dev caching guidance](https://web.dev/learn/pwa/caching); neither document substitutes for physical-device acceptance.
