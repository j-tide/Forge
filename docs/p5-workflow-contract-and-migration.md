# P5 Workflow contract and migration

## Source of truth and transport

The read-only product contract is `forge_spec_v1.0/contracts/workflow.schema.json` (`schemaVersion: "1.0"`). Production checks use the closed `WorkflowTemplate` Pydantic model in `python/src/forge/workflow_templates.py` and the matching Zod model in `packages/contracts/src/workflow.ts`. A saved draft, published revision and frozen RunConfig keep separate IDs/revisions/hashes; a canvas layout is local presentation data and never part of the Host Workflow hash. Unknown fields or schema versions are rejected. Future `schemaVersion` values return `WORKFLOW_DSL_VERSION_UNSUPPORTED` from Python Host; Desktop canvas import explains the required version without changing the input document or stored rows.

The reference `forge_spec_v1.0/contracts/openapi.yaml` describes a **future Host Gateway**. No HTTP service is running in the Desktop implementation, so P5 adds no OpenAPI path and does not claim the gateway methods exist. Current local calls are allowlisted JSON-RPC over stdio (`forge-local-jsonrpc/v1`, Host protocol `forge-host-protocol/v5`), using `workflow.presets/list/get/impact/saveDraft/compileDraft/publish`, `run.config` and `context.sources`. Electron Main checks sender, timeout and closed Zod request/response; Python Host checks strict Pydantic. `run.config` and `context.sources` are read-only, Project/Run scoped and omit raw provider events, database paths and secrets. A future Remote adapter must define authentication/scopes before mapping these operations to HTTP; the reference OpenAPI remains a design contract, not an enabled endpoint.

Published does not mean runnable. At P5 the Python Host admits only a published four-node quick-shaped Develop→Review→Verify→human owner chain that matches the exact compiled version and available capability catalog. It freezes the Workflow and Developer/Reviewer Profile versions/hashes in the RunConfig. Other valid definitions may be saved/published but fail closed at runtime with `WORKFLOW_RUNTIME_UNSUPPORTED` or `WORKFLOW_RUNTIME_UNAVAILABLE`. Review, Verify and final acceptance require separate actual evidence and user/API action; no stage is marked complete because a node exists on the canvas. If a Run requests retrieval, conflicts or no source prevent launch; accepted citations are frozen with trust labels. Revoking a source removes current retrieval but leaves the historical Run bundle and a revoked status.

## Upgrade and recovery

SQLite is owned only by the Python Host. The additive P5 migrations are schema 26 (Workflow drafts and immutable published revisions), 27 (Project knowledge), 28 (scoped FTS), and 29 (Project memory and audit). They do not rewrite P3/P4 Task, approval, Run, Profile or merge tables. A populated independent schema-25 fixture with an approved Task, queued Run, frozen RunConfig and P4 Agent Profile was upgraded through schema 29 twice, then reopened: all four records retained their IDs and content, foreign key check was clean, and a WAL-aware backup existed. This tests a fixture, **not** an actual user's database; production user-data upgrade, installer and Windows/macOS Intel remain unverified.

Existing P3-11 resilience tests remain applicable: transaction crash without half-commit (T086), WAL online backup/restore and foreign keys (T087), failing migration rollback/read-only recovery (T088), SQLite full write failure without false success (T089), and plugin storage namespace isolation (T090). The P5 schema-25→29 populated upgrade is additional evidence, not a replacement for these tests. No reset, prune, source repository deletion or automatic user-data migration is performed by this document. On a future-version/corrupt DSL, stop the operation, surface the diagnostic and keep the original row for an explicit compatible migration; do not coerce it to v1 or silently execute a different Workflow.

## User guidance

1. In Forge Desktop, trust a Project and open Workflows. Start from a bundled template, bind currently available Developer and read-only Reviewer Profiles, inspect compile diagnostics, then explicitly save and publish. Publishing never starts a Run.
2. To import canvas JSON, use `forge-workflow-canvas/v1` with a `definition.schemaVersion` of `1.0`. An incompatible version shows a specific error and leaves the current draft unchanged. Exported layout coordinates do not alter Workflow semantics.
3. Approve a Task Contract before starting a Run. Only the supported published quick-shaped chain can start. A retrieval query is optional; when entered, no answer or contradictory sources block launch for human correction. The Executor receives tagged citations as guidance, never as Task acceptance criteria.
4. Inspect the Run Context tab for the actual node, frozen Workflow/Profile identity and source status. A revoked source is a historical warning, not a retroactive edit to the completed Run. Review, Verify and owner acceptance remain separate steps. Done does not mean merge, push or deploy.

See [ADR 0067](decisions/0067-published-linear-workflow-runtime-and-retrieval-freeze.md) for the runtime admission decision. Claude P4-05 and the full P4 multi-Executor release gate remain blocked; this guide describes one verified Codex Executor path.
